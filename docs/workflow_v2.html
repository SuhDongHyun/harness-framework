계획은 에이전트가,
판정은 증거가.

현재 프로젝트는 한 개의 계획을 승인한 뒤, 단일 실행 레인에서 각 단계를 순차 실행·재시도하고 독립 명령으로 검증하는 Python 3.11+ 하네스다. 상태 변경 권한은 컨트롤러에 집중되어 있고, Git 스냅샷과 실행 메타데이터 스냅샷이 에이전트의 작업 경계를 감시한다.

01 / SUMMARY

현재 구현 요약

“개인용 Codex 작업 오케스트레이터”의 1단계 골격이 완성된 상태다. 계획 생성과 실제 수정 권한을 분리하고, 승인 시점의 저장소 상태를 실행 직전까지 고정한다.

01

계획

Codex를 read-only로 실행해 스키마 기반 draft plan을 만든다.

02

승인

사용자가 편집한 최종 계획의 SHA-256과 현재 Git fingerprint를 고정한다.

03

실행

각 step을 workspace-write로 순차 실행하고 범위 위반을 사후 탐지한다.

04

독립 판정

에이전트의 완료 주장을 신뢰하지 않고 acceptance command의 실제 종료 코드로 판정한다.

핵심 설계 문장: 모델 출력은 구조화된 보고서일 뿐이다. 완료의 근거는 컨트롤러가 직접 실행해 저장한 검증 명령 evidence다.
02 / ARCHITECTURE

구성 요소 지도

cli.py가 객체를 조립하고, controller.py가 정책을 집행한다. Runner와 Verifier는 모두 subprocess를 다루지만 신뢰 수준과 역할이 다르다.

scripts/harness.py

저장소 루트를 Python 경로에 넣는 실행 진입점

harness/cli.py

명령 파싱, 의존성 조립, JSON 출력과 종료 코드 결정

harness/config.py

TOML 설정 로딩 및 범위 검증

harness/controller.py

plan → approve → run → verify 상태 전이의 유일한 소유자. Git 경계, 메타데이터 무결성, retry, terminal state를 결정한다.

harness/models.py + schemas/

계획·단계 결과·상태의 직렬화 계약과 추가 안전 검증

harness/store.py

run artifact의 원자적 저장, 이벤트 append, 스냅샷 복원

harness/runner.py

Codex CLI 실행, JSONL 이벤트 및 구조화 최종 출력 수집

harness/verifier.py

승인된 argv 명령을 shell 없이 실행하고 독립 evidence 생성

harness/git_guard.py

브랜치·HEAD·index·dirty path의 읽기 전용 스냅샷과 변화 계산

03 / WORKFLOW

끝에서 끝까지

정상 실행은 7개의 큰 구간을 통과한다. 각 step의 에이전트 실행과 검증 사이에 Git 및 하네스 메타데이터 검사가 끼어 있다.

draft1. Planread-only Codex가 plan schema에 맞는 계획 생성
approved2. Approveplan hash + Git fingerprint 기록
running3. Step runCodex workspace-write 실행, JSONL 수집
guard4. Boundarymetadata, evidence, branch, HEAD, index, path 검사
verifying5. Verifystep acceptance command 순차 실행
retry6. Retry실패 evidence를 다음 prompt에 전달
completed7. Final전체 acceptance 후 terminal state 확정

plan(goal)

공백 goal을 거부하고 run directory를 먼저 만든다. Codex에는 계획 작성 전용 prompt, read-only sandbox, plan.schema.json을 넘긴다. 프로세스 성공 조건과 Plan.from_dict 검증을 모두 통과해야 plan.json, step markdown, 초기 state.json이 저장된다.

approve(run_id)

plan과 state가 모두 draft인지 확인한다. draft 동안 사용자가 plan.json을 편집할 수 있으므로 승인 시 step 문서와 state를 다시 만든다. approved plan hash와 Git snapshot fingerprint를 저장해 이후 변조를 감지한다.

run(run_id)

승인된 plan hash와 현재 plan이 일치하고, Git fingerprint도 승인 당시와 동일해야 시작한다. step마다 최대 max_retries회 Codex를 호출하고, 에이전트가 completed를 보고한 경우에만 acceptance command를 실행한다.

_verify_with_guard(...)

검증 전후 Git 및 모든 runs 파일을 비교한다. 테스트·lint 자체가 저장소 파일, Git branch/HEAD/index 또는 controller metadata를 바꾸면 명령의 exit code가 0이어도 safety failure로 처리한다.

step 한 번의 실제 판정 순서

#행동통과 기준 / 실패 결과
1state를 running, attempt를 현재 번호로 저장컨트롤러가 원자적으로 기록
2Git snapshot과 전체 runs artifact snapshot 확보비교 기준선 생성
3Codex 실행exit 0 + timeout 아님 + 마지막 terminal event가 turn.completed + 유효 final object + malformed/truncation/reader error 없음
4runs 파일 변조 복원 및 분류현재 attempt event log만 새 evidence로 허용. metadata 또는 과거 evidence 변조면 즉시 failed
5Git 경계 검사branch/HEAD/index 불변, 실제 changed path가 모두 step allowed_paths에 포함
6StepResult 해석blocked는 즉시 중단, failed는 retry, completed만 검증 진입
7acceptance commands모든 명령 exit 0 + 검증 과정이 어떤 파일·Git·run metadata도 변경하지 않음
8성공 또는 retry성공 summary는 다음 step prompt에 전달. 실패 evidence는 같은 step의 다음 attempt prompt에 전달
04 / STATE MODEL

상태 전이

Plan status, run status, step status는 분리되어 있다. terminal_result는 run의 최종 결과만 completed / failed / blocked 중 하나로 기록한다.

Run

draft→ approve → approved→ run → running→ steps done → verifying→ completed 또는failed /blocked

Step

pending→ running→ agent completed → verifying→ completed 검증/실행 실패 시retrying↺ running 끝failed/blocked
재실행 모델: run()은 오직 approved 상태에서만 시작한다. 중간에 failed/blocked/running으로 끝난 run을 이어서 재개하는 경로는 현재 없다.
05 / ARTIFACTS

run별 산출물

RunStore가 관리하는 논리 구조다. 실제 root 설정 내용은 분석하지 않았으며, 코드상 runs_root/run_id 아래에 다음 파일이 생성된다.

runs_root/
└── <run-id>/
    ├── request.md                       # 원본 goal
    ├── plan.json                        # draft → approved plan
    ├── state.json                       # controller-owned 현재 상태
    ├── approved-git.json                # 승인 시 Git snapshot
    ├── events.jsonl                     # 상태 전이 감사 로그
    ├── steps/
    │   └── 00-<step-name>.md            # 사람이 읽는 step 명세
    └── evidence/
        ├── plan-events.jsonl            # 계획 Codex event stream
        ├── step-00-attempt-01.jsonl     # 실행 Codex event stream
        ├── step-00-attempt-01-agent.json# runner 결과 + 실제 changed paths
        ├── step-00-attempt-01-verification.json
        └── final-verification.json

원자적 저장

임시 파일을 같은 디렉터리에 쓰고 fsync 후 os.replace하여 중간 상태 노출을 줄인다.

append-only 이벤트

각 이벤트에 UTC timestamp를 자동 추가하고 한 줄 JSON으로 append + fsync한다.

변조 복원

에이전트 실행 전 모든 run 파일을 캡처하고, 예상하지 않은 변경을 복원한 뒤 run을 실패시킨다.

07 / SCHEMAS

schemas/ 데이터 계약

세 파일 모두 JSON Schema draft 2020-12, version 1 계약이다. plan과 step-result는 Codex의 --output-schema에 직접 사용된다.

plan.schema.json

goal, draft|approved, 1–100개의 step, final commands를 정의한다. 각 step은 ID/name/objective/read/allowed/acceptance/forbidden의 정확한 7필드다.

추가 Python 검증: 순차 ID, path escape, metadata 경로, 위험 명령 차단.

step-result.schema.json

에이전트가 내는 completed|failed|blocked, summary, changed files, error, blocker, required action의 정확한 6필드다.

changed_files는 보고용이며 실제 범위 판정은 GitGuard 측정값을 쓴다.

state.schema.json

run 상태, 승인 hash/fingerprint, current step, step별 attempts/summary/error, terminal result를 문서화한다.

Codex output에는 사용하지 않고 doctor가 JSON parse 여부를 확인한다. 실제 read 검증은 RunState.from_dict가 맡는다.

Schema와 모델의 차이: schema의 path는 단순 non-empty string이지만 Python 모델은 repository escape를 막는다. schema의 command는 단순 argv array지만 모델은 shell·파괴 명령·inline interpreter·쓰기 Git 명령을 막는다. 즉 런타임 모델이 더 강한 계약이다.

10 / SAFETY

안전 경계의 층

하나의 sandbox에만 의존하지 않고 입력 계약, 승인 baseline, 실행 후 측정, verifier 부작용 탐지를 겹쳐 놓았다.

입력 단계

정확한 JSON key, 안전한 상대 경로, reserved metadata 제외, argv 형태, 위험 executable/Git command 거부.

승인 단계

canonical plan hash와 branch/HEAD/porcelain/dirty content/index를 포함한 Git fingerprint 고정.

실행 단계

Codex event/output 제한, timeout process-group kill, 모든 run metadata snapshot 복원, allowed path 비교.

검증 단계

shell 없는 argv 실행, 첫 실패 중단, stdout/stderr bounded evidence, 검증 자체의 파일 및 Git 변경 거부.

상태 단계

state를 컨트롤러만 쓰며 전이마다 원자 저장하고 append-only event로 감사 흔적을 남긴다.

신뢰 모델

에이전트의 changed_files·completed 보고보다 GitGuard의 실제 관측과 Verifier 종료 코드를 우선한다.

11 / LIMITS

현재 구현의 경계

결함이라는 뜻보다는, 지금 코드가 제공하는 보장과 제공하지 않는 보장을 구분한 것이다.

단일 레인 · 순차 실행

step 병렬 실행, dependency graph, worktree 분리 없이 plan 순서대로만 실행한다.

중단 run 재개 없음

run() 시작 조건이 approved뿐이라 failed/blocked/running 상태의 resume/recovery 경로가 없다.

failed attempt 변경은 누적

retry 전에 repository를 되돌리지 않는다. 다음 attempt는 앞선 attempt가 남긴 허용 범위 내 변경 위에서 계속 작업한다.

코드 변경 자동 복원 없음

out-of-scope 또는 verifier mutation을 탐지해 실패시키지만 repository 파일은 되돌리지 않는다. 자동 복원은 run metadata에만 적용된다.

read_files는 안내

실행 sandbox는 workspace 단위다. 나열된 파일만 읽도록 OS 수준에서 제한하지 않고 prompt로 지시한다.

forbidden_changes는 안내

일반 자연어 제약은 prompt에 들어가지만 기계적으로 해석하지 않는다. 실제 강제는 allowed path와 Git/meta guard가 담당한다.

보고 경로와 실제 경로 미대조

StepResult.changed_files는 계약상 검증되지만 GitGuard가 측정한 changed_paths와 동일한지 비교하지 않는다.

final command는 0개 가능

step acceptance는 최소 1개지만 final acceptance는 빈 배열도 유효하며, 이 경우 모든 step 성공 후 final verification은 자동 성공한다.

Schema validation의 역할 차이

state.schema.json을 별도 validator로 실행하지 않는다. 저장 상태의 실제 검증은 Python 모델이 수행한다.

프로세스 안전의 플랫폼 차이

POSIX는 process group 전체를 kill하지만 Windows 코드는 직접 process kill만 수행한다. 관련 child-process tests도 Windows에서는 skip된다.

12 / ASSESSMENT

개발 상태 판단

코드와 테스트만 기준으로 보면 “설계 초안” 단계는 지났고, 제한된 phase-one 워크플로를 실제로 수행할 수 있는 작은 MVP다.

구현되어 있는 것

계획 생성, 사용자 승인, 승인 무결성, step 순차 실행, 실패 evidence 기반 retry, blocker 전파, step/final 독립 검증, Git·index·metadata 경계, audit artifact, doctor CLI가 연결되어 있다.

아직 확장하지 않은 것

병렬성, 실행 재개, 자동 rollback, 세션 복구, UI/dashboard, 외부 orchestration, 복잡한 정책 엔진은 없다. 현재 구조는 이를 억지로 추상화하지 않고 한 controller lane에 집중한다.

한 줄 결론: 이 프로젝트는 “Codex가 작업하되 Codex가 자기 성공을 판정하지 못하게 하는” 개인용 순차 실행 하네스의 핵심 루프와 방어선이 구현된 상태다.

이 문서는 harness/, schemas/, scripts/, tests/의 2026-08-02 작업 트리 내용을 기준으로 작성되었다. 제외 요청된 디렉터리와 기존 문서의 내용은 분석에 사용하지 않았다.
